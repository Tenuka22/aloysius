# Flat club content implementation

- Keep the club slug list in `packages/db/src/schema/club-photos.ts` (`CLUBS`) as the single source of which clubs exist. There is no `club` registry table, no club profile, and no per-club config constant in the API — a club is just a string every content table's `club` column is `CHECK`-constrained against.
- Keep authentication users in the existing Better Auth `user` table; identify a club admin by the hardcoded username and the `club-admin` role.
- Authorise with Better Auth's access control: `requireClubPermission("submit" | "read")` for the four club-admin screens, `clubReviewerProcedure` (`requireRole("admin", "cms")`) for the four CMS review screens, `publicProcedure` for the four public reads.
- Each content type — photo (`club_photo`), announcement (`announcement`), event (`event`), news post (`news_post`) — gets six endpoints in `packages/api/src/routers/club/`, one file per endpoint: `submit*`, `listMy*`, `withdraw*`, `listPending*`, `review*`, `listApproved*`. `announcement` and `event` are shared tables with CMS-authored school-wide rows, distinguished by the `club` column; `club_photo` and `news_post` are club-only tables.
- Every table carries `status` (`pending`/`approved`/`rejected`), `submittedById`, and `reviewedById`/`reviewedAt`/`reviewNote`, with a `*_review_fields_paired` CHECK pairing the three reviewed-at-once. `review*` writes all three in one `update … set` call so the CHECK can never be tripped by a partial write.
- `submit*` inserts the row directly — no proposal table, no JSON payload, no base-snapshot, no separate applier. `review*` is the entire publish step: setting `status = 'approved'` is what every `listApproved*` query selects on, so there is nothing else to forget to run.
- `withdraw*` deletes a still-`pending` row scoped to `submittedById`; once a row leaves `pending` the decision and its `reviewNote` are the record worth keeping, so withdrawal is refused.
- `club_photo.fileId` must already exist and belong to the caller (checked against `files.userId`) before a submission is accepted; the image itself goes through the existing upload-then-confirm flow, not through the submission endpoint.
- Public reads (`listApproved*`) take no session and filter only on `club` + `status = 'approved'`; `club_photo`'s read additionally resolves `fileId` to a URL via the files router, since an anonymous visitor cannot call the authenticated file-resolution path.
